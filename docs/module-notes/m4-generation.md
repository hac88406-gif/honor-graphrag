# M4 模块说明 — 生成层（云端 LLM + 生成后校验）

> 规格书 9.1-1：每个模块交付时附带三段说明（为什么这么设计 / 会被问什么 / 怎么答）。
> 覆盖 `app/llm/`（`client` / `prompts` / `guard`）与 `app/agent/nodes/generate.py`，
> 以及 M3 审核三项修改中落到本层/本批的部分（置信度按路径定义、多意图告知）。

## 1. 为什么这么设计

**为什么生成层单独一个包，而不是写在节点里。**
`generate.py` 一个文件同时塞下「怎么调云端」「prompt 长什么样」「生成完怎么校验」，
任何一处要改都得翻同一段代码，而且 prompt 是评测时最常调的东西 —— 混在节点里无法对照
失败样本批量迭代。故拆成三个职责单一的模块，边界清晰：

| 模块 | 职责 | 是否碰网络 |
| --- | --- | --- |
| `prompts.py` | prompt 集中维护（4.9 明确要求，禁止散落在节点） | 否（纯函数/纯常量，可离线单测） |
| `client.py` | 云端客户端：reasoning 隔离 + 空答案 fail-fast | 是（唯一碰网络的地方） |
| `guard.py` | 生成后校验（第二道防线） | 否（确定性启发式，**不调用 LLM**） |

**为什么 prompt 之外还必须有生成后校验（这是本层最核心的设计）。**
4.9 的生成约束第一条是「答案只能来自 evidence」。原方案只靠 prompt 把这条讲清楚。
但需求方 2026-10-15 实测 + 本机 `scripts/compare_llm_models.py` 复跑都显示：给两条资料
（含「妲己克制后羿，因后羿怕高爆发法师」），`deepseek-chat` / `deepseek-v4-pro` / `deepseek-flash`
在**基础 prompt 与强化 prompt 下均**答成「后羿怕高爆发法师（比如妲己）」—— 把资料里的
**解释**当成了**类别**（4/4 命中）。这证明 **prompt 无法单独阻止该类外推**，
所以必须有第二道防线：`guard.check_answer` 在答案交付给用户**之前**拦下并回落。

**为什么 guard 是确定性启发式，而不是再调一次 LLM 去判断。**
把「答案是否越界」交给另一个模型判断，等于把最关键的安全机制交给最不稳定的组件 ——
它可能这次判对、下次判错，且无法离线单测、无法复现。启发式规则（正则 + 实体链接比对）
是确定性的：同样的输入永远同样的判定，可写死断言、可离线跑、可复现。
代价是只能覆盖**已观测**的失败形态，这一局限在 `guard.py` 模块头与 M4 报告里如实标注。

**为什么 guard 的规则是「量出来的」而不是「拍出来的」（二审裁定 B-1）。**
G3 是正则匹配，天然会误伤 —— 官方 reason 本身常含「刺客/射手/法师」这类职业词，
模型**正当引述**它会不会被拦？需求方要求把这件事**量化**，误报 >20% 就得放松。
`scripts/measure_guard_fp.py` 从真实 `relations.json` 筛测例（挑「reason 本身就会触发 G3」的边，
即误报风险最高的样本，而非手编），在**同一批模型回答**上对照两条规则：
**放松前拦下 8 例，逐例判定后真越界仅 1 例、误报 7 例（FP=87.5%）**；加两条豁免后
**拦下 1 例，即那 1 例真越界（FP=0%）**。两条豁免都钉了边界用例，防止被放大成「一律不判」：
R1 仅在问题**问原因**时生效，R2 按**命中位置**判（而非「答案里出现过该英雄名」）。
代价如实标注：问「为什么」时模型自己编造类别会漏过 —— guard 是启发式**下限**不是安全底线，
**误拦（把正常回答降级成机械证据罗列）的代价大于漏拦**。

**为什么 G2 词典不可用时是「放行但可见」（二审裁定 B-2）。**
词典（实体链接）不可用时 G2 无从判定，此时**不能**改成拦截 —— 那是拿一个不工作的检查去误伤
正常回答。但也不能只 `logger.warning`：**日志没人看就等于静默消失**。故降级标记一路透传
`GuardResult.degraded` → `generation_info.guard_degraded` → `debug.guard_degraded`，
`/api/chat/sync` 的 `debug` 块里能直接看到「这一轮 G2 没生效」。

**为什么失败一律回落「确定性证据组装」，而不是重试或让模型改写。**
重试会引入「这次行不行」的不确定性，还可能把同样的越界答案换一种说法再给出来；
让模型「修正」越界答案属于二次生成，同样不可控。而 `_template_body` 逐条摘录 evidence，
**构造上不可能**引入 evidence 之外的事实 —— 它是本项目唯一「一定正确但可能不够漂亮」的兜底。
生成失败时宁可交付朴素但可溯源的证据列表，也不交付看起来流畅但可能越界/为空的模型答案。

**为什么成功判定是「content 非空 AND finish_reason != 'length'」而不是 HTTP 200。**
需求方实测：`max_tokens=200` 时重问题返回 **HTTP 200 + `finish_reason='length'` + `content=''`**。
只看 HTTP 状态码，一个「成功」的响应里藏着空答案，会被当成正常回答往下走 —— 典型的静默失败。
本机 `scripts/verify_m4_generation.py` 段 E 复现了这一形态并确认被拦下。原配置 `512` 同样危险
（思考吃 250~290，留给正文仅 220~260），故 `LLM_MAX_TOKENS` 提到 **2048**。

**为什么 `reasoning_content` 要单独一个字段、流式还要单独推一个事件。**
flash 与 v4-pro 都是**推理模型**：响应除 `content` 外还有 `reasoning_content`，
且 `completion_tokens` **包含思考**（实测同一问题 chat=40 / v4-pro=253 / flash=287）。
若不隔离，思考过程会被当成答案展示给用户，token 账目也会算错。
故 `LLMResult.reasoning` 与 `content` **分开返回**；流式时 reasoning 分片只触发一次
`thinking` 事件（「正在思考」提示），**不得混入正文**。新增 `thinking` 事件属对 5.3 事件集合的
**有意扩展**，已登记 DECISIONS。

**为什么模型名一律取自配置、代码里不写死。**
需求方实测 `GET /models` 只返回 `['deepseek-flash','deepseek-v4-pro']`，**没有** `deepseek-chat`
（后者仍可调，是未列出的兼容别名）。若代码硬写某个名字，就出现「配置与可用清单不一致」的隐性依赖。
故 `CLOUD_CHAT_MODEL` 只来自 `.env`，`client` 里任何地方都不出现字面量模型名（9.1-2）。

**为什么加 `GENERATION_MODE`（llm / template）这个开关。**
生成接入云端后，M3 的集成用例（四条追问链、降级、API 冒烟）会因每次调用云端而变慢、依赖网络、
结果不确定。把生成方式做成配置后，`tests/conftest.py` 全局钉住 `template`，
既有用例保持**离线、确定性、可复现**；M4 的生成用例显式切 `llm` 并注入假客户端。
这不是「为测试开后门」—— 它同时是 M6 评测对照实验（模型答 vs 确定性组装）的开关。

**为什么置信度判定改为「按检索路径分别定义」（M3 审核·修改二，本批落地复核）。**
M3 的保守口径用「向量相似度」一把尺子量所有证据，于是 `COUNTER_BY/COUNTER_OF/SYNERGY/INSCRIPTION`
四个**图谱单路**意图一旦没有相似度可比（`top_score is None`）就被一律打成 `low_confidence` ——
把最可靠的官方 curated 关系贴上了最弱的标签。4.9 v1.5 的修正原则是 **缺失 ≠ 低质量**：
每一路用**它自己**的依据维度来判（图谱侧看关系条数、文本侧看 top1 相似度、混合路取更保守者）。
`scripts/verify_m4_generation.py` 段 F 实测：「铠被谁克制」图谱返回 4 条官方事实，
现在判 `answer` + `confidence=0.85`，而不是 M3 的 `low_confidence`。

**为什么「多意图告知」放在生成层（M3 审核·修改三）。**
此前只做到「留痕」（`matched_intents` + 日志 warning），用户仍拿到半个答案而不知情。
告知文案属于**答案的一部分**，必须在生成层拼进 `answer`（且流式时前缀行先推），
否则前端拿到的正文里看不出「本次只回答了哪个意图」。**仍不做多意图合并** —— 二审**裁定 A**
已把口径改为「**由 M6 的数据决定做不做**」（先测复合意图在真实问句中的占比再定），见 DECISIONS。

**为什么流式用 `astream(stream_mode=[...])` 而不是 `astream_events`。**
4.8-6 原文写 `astream_events`。但实测（LangGraph 1.2.15）该接口**拿不到节点内
`get_stream_writer()` 推的自定义事件**（thinking / token），只暴露框架内建事件。
故改用 `astream(stream_mode=["custom","updates","debug"])` 三路合一：
`custom` 拿节点内事件、`debug` 拿节点启动边界、`updates` 拿 fuse 的证据增量。
对 5.3 的 SSE 协议无影响，偏离已登记 DECISIONS。

**为什么 Ollama 不可达不会让链路报错。**
`LLM_MODE=hybrid` 下意图默认走**确定性规则**（`route(use_llm=False)`，见 DECISIONS 2026-10-14），
生成走云端，Ollama 只在两条路径上被触及：`/api/health` 的探测（失败只回状态不抛）
与可选增强 `route_llm`（仅 `use_llm=True` 时调用，整体包在 try/except 里回落规则）。
`tests/unit/test_ollama_offline.py` 把这一点固化成断言 —— 可选路径最容易在某次重构里被改成默认路径，
届时本机没起 Ollama 的演示环境会直接 500。

## 2. 会被问什么

1. 为什么 prompt 之外还要加生成后校验？prompt 为什么不够？（用 4/4 越界的实测回答）
2. 校验为什么不用 LLM 做？启发式的边界在哪？漏过了怎么办？
3. 生成失败为什么回落「证据组装」而不是重试或让模型改？回落会不会影响回答质量？
4. 「HTTP 200 但是空答案」是怎么回事？为什么不能用状态码判断成功？
5. `reasoning_content` 是什么？为什么必须隔离？成本怎么算才不亏？
6. 流式怎么保证思考不混进正文？`thinking` 事件为什么算对 5.3 的扩展？
7. 为什么模型名不写死在代码里？
8. `GENERATION_MODE=template` 是不是为了测试作弊？
9. 置信度为什么要按检索路径分别定义？「图谱单路无相似度」这一格原来错在哪？
10. 多意图告知和「多意图合并」的区别是什么？
11. 为什么不用 `astream_events`？
12. guard 的误报率怎么测的？为什么用真实数据筛测例而不是手编？（二审 B-1）
13. 两条豁免（R1/R2）会不会把真越界也放过？边界钉在哪？
14. G2 词典不可用时为什么放行而不是拦截？运维/前端怎么知道它降级了？（二审 B-2）

## 3. 怎么答

- **prompt 不够**：4.9 的生成约束第一条是「答案只能来自 evidence」。实测给两条资料
  （含「妲己克制后羿，因后羿怕高爆发法师」），三个模型在基础/强化 prompt 下**都**答成
  「后羿怕高爆发法师」——把资料里的**解释**当成了**类别**（4/4）。prompt 能约束「别编造事实」，
  但约束不住「把给定事实做抽象/外推」，故必须有生成后校验。
- **guard 不用 LLM**：把安全判定交给最不稳定的组件是反模式；启发式确定性、可离线单测、可复现。
  三条规则：G1 空答案、G2 英雄名越界（实体链接比对，答案里的英雄名必须在资料或问题里出现）、
  G3 类别化外推（正则拦「怕…法师」「法师克制…」两种语序）。
- **guard 的误报率是量出来的**（二审 B-1）：`measure_guard_fp.py` 从真实 `relations.json` 筛
  「reason 本身触发 G3」的边出题（误报风险最高的样本），**同一批模型回答**上对照两条规则 ——
  **放松前 FP=87.5%（拦 8 例，仅 1 例真越界）→ 放松后 FP=0%（拦 1 例即真越界）**。
  两条豁免：**R1** 问题在问「原因」时不判（引述 reason 是合规行为，不是类别化外推）；
  **R2** 命中片段落在含职业词的英雄名内时不判（如「元流之子(法师)」，职业词是英雄名的一部分）。
  **边界钉死**：R1 仅对问原因的问句生效、R2 按**位置**判，6 个单测防止豁免被放大成「一律不判」。
  **代价如实说**：问「为什么」时模型自己编造类别会漏过 —— 误拦的代价大于漏拦。
- **G2 降级可见**（二审 B-2）：词典不可用时 fail-open（放行、不误拦），但降级标记透传到
  `debug.guard_degraded`，不再只写日志 —— 日志没人看等于静默消失。
- **guard 局限**：只覆盖已观测形态，是**下限不是保证**；M6 按裁定 B-3 做 guard on/off 的 A/B 对比，
  量化它对「答案有据率」的实际影响。
- **失败回落**：`_template_body` 逐条摘录 evidence，**构造上不可能**引入外部事实，是唯一
  「一定正确」的兜底。失败原因写进 `state.error` 与 `debug.generation`，绝不静默。
- **空答案**：`max_tokens=200` 时重问题返回 `HTTP 200 + finish_reason='length' + content=''`。
  故成功判定固化为 `content` 非空 **AND** `finish_reason != 'length'`，不满足即抛
  `LLMGenerationError`，由节点回落。`LLM_MAX_TOKENS` 由 512 提到 2048（思考吃 token）。
- **reasoning**：推理模型的思考在 `reasoning_content` 里，与 `content` **分开返回**；
  流式时 reasoning 分片只推一次 `thinking`（「正在思考」），不进正文。
  成本统计用 `completion_tokens`（**含思考**），可用 `completion_tokens_details.reasoning_tokens` 拆分。
- **模型名**：`GET /models` 不含 `deepseek-chat`（兼容别名），故一律取 `CLOUD_CHAT_MODEL`，
  代码不出现字面量模型名。
- **`GENERATION_MODE`**：不是测试后门 —— 它让 M3 的既有用例保持离线确定性，
  同时是 M6「模型答 vs 确定性组装」对照实验的开关；生产/演示置 `llm`。
- **置信度按路径**：图谱单路看**关系条数**（≥3→0.85 / 2→0.75 / 1→0.60，**≥1 条即正常回答**）；
  向量单路看 top1 相似度（≥CONF_HIGH 且 ≥2 条文本证据才正常）；混合路取**更保守者**，
  仅单侧有据则降级。核心原则是「缺失 ≠ 低质量」，别用一把尺子量所有证据。
- **多意图**：告知 = 答案里说明「本次只回答了 X，还可继续追问 Y」；**合并不做** —— 二审裁定 A：
  口径改为「由 M6 的数据决定做不做」（先测复合意图占比，低则永久不做并写进 README 已知局限）。
- **流式**：`astream_events`（1.2.15）拿不到节点内自定义事件，改用
  `astream(stream_mode=["custom","updates","debug"])`，对 5.3 协议无影响。
