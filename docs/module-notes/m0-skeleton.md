# M0 模块说明 — 骨架与环境

> 规格书 9.1-1：每个模块交付时附带三段说明（为什么这么设计 / 会被问什么 / 怎么答）。

## 1. 为什么这么设计

**配置集中在 `app/config.py` + `.env`，不硬编码。**
规格书 9.1-2 要求所有配置项（模型名、路径、阈值、端口）从统一入口读取。用 `pydantic-settings` 而不是手写 `os.getenv`，理由是它自带类型转换与默认值，且能在启动时对类型错误直接报错——阈值写成字符串这类问题会在启动瞬间暴露，而不是在检索时才表现为"莫名其妙的拒答"。`.env.example` 入库、`.env` 不入库（含口令），是标准做法。

**`/api/health` 三项状态各自独立探测，失败不抛错。**
三项组件（neo4j / chroma / llm）任一不可用，都不能让 health 接口本身 500——否则运维/演示时"想知道谁挂了"反而先被接口错误挡住。因此每项探测各自 try/except，返回 `{ok, detail}`，detail 里带上原始异常文本，便于定位（这是规格书 9.1-6"记录关键中间结果便于排查静默失败"在健康检查上的应用）。

**Neo4j / Chroma 的导入写在函数内部（延迟导入）而非模块顶层。**
这样 M0 阶段即使某个组件不可用，应用仍能启动、health 仍能返回三项状态；组件缺失表现为 `ok:false + ModuleNotFoundError`，而不是 import 阶段崩溃。这与规格书 4.12"外部依赖只有 Neo4j 一个、其余可降级"的思路一致。

**依赖拆成两份清单（`requirements.txt` / `requirements-ml.txt`）。**
M0 只需要 Web 框架 + 客户端 + 测试；`sentence-transformers` 会连带 torch（Windows 上 GB 级下载）。拆开可让 M0 快速验证骨架，不被重依赖阻塞。见 DECISIONS.md。

**Redis 不引入。**
规格书 2.3/2.4 已裁定：多轮记忆交给 LangGraph checkpointer（`SqliteSaver`），Redis 完全移除，中间件依赖从 3 个降到 1 个。

## 2. 会被问什么

1. 为什么用 `pydantic-settings` 而不是 `python-dotenv` 直接读环境变量？
2. `/api/health` 为什么返回 `ok:false` 而不直接返回 503？
3. 为什么 `neo4j` / `chromadb` 要延迟导入？
4. 项目为什么只有一个外部中间件（Neo4j）？Chroma 和会话记忆为什么不需要 Docker？
5. 配置项里 `PATCH_WINDOW` 为什么用列表而不是动态计算？

## 3. 怎么答

- **pydantic-settings**：配置即类型化对象，启动时校验；阈值/端口写错立刻报错，而不是等到运行时表现为"行为诡异"（本项目反复强调的静默失败防御）。
- **health 不返回 503**：health 的语义是"报告状态"而非"表示自身健康"。三项独立探测 + 不抛错，让调用方一次拿到完整诊断信息；503 会掩盖"到底哪一项挂了"。
- **延迟导入**：让组件故障降级为数据面的 `ok:false`，而不是进程级的启动失败；对应规格书 4.8-5"不允许直接抛 500"。
- **只有一个外部依赖**：Chroma 用嵌入式 `PersistentClient`（进程内、零外部服务）；记忆用 LangGraph `SqliteSaver`（本地 SQLite 文件）。Redis 已被 2.3 的修正移除。所以真正要外部起的只有 Neo4j。
- **`PATCH_WINDOW` 用显式列表**：1.9 裁定统一口径为"最近 3 个 patch"。用显式列表而非运行时计算，是为了让窗口可被配置、可被评测阶段复现；当前值 `["2026-10","2026-09","2026-08"]` 与 `CURRENT_PATCH=2026-10` 一致。
