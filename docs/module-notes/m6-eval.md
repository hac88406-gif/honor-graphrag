# M6 模块说明 — 评测（评测集 / 判官 / 测量脚本 / 会话清理）

> 规格书 9.1-1 / 附录 B：每模块三段说明。M6 的「模块」不是业务节点，而是**评测装置**——
> 它决定这个项目能否被证明是工作的，故单独成篇。

---

## 1. 为什么这么设计？

**（a）覆盖集与泛化集必须分开，且不得混算。**
`cases.yaml`（38 条）按 8.1 六类分布手工构造，每条带 `expected_intent` / `expected_entity_ids` /
`expected_evidence_contains`；`freeform.yaml`（74 条）是真实用户口吻的自由问句。
两者混算会出现两种失真：① 用大样本把覆盖集的问题稀释；② 用小样本把泛化集的置信区间做窄。
分开报后，覆盖集 97.6% 与泛化集 85.1% 的**差距本身**就是最有价值的信号——
它精确指出「规则关键词表覆盖不到自由口语」是当前唯一的主要误差源。

**（b）判据必须单一来源，否则两个比例不可比。**
8.2 的「答案有据率」与需求方的「guard 误报率」本质是**同一个判断**（答案是否超出给定依据），
故 `scripts/eval_judge.py` 是唯一 rubric，`measure_grounded.py` 与 `measure_guard_blocked.py` 共用。
若各写一套「有据」标准，两个数就没法互相印证。判官用 **LLM 而不是规则**：guard 本身是规则，
再用同一套规则判它准不准就是**自证**；代价是判官有噪声，故对判 False 的每条都附原文供人工复核，
并明确标注「判官是 LLM，不是独立第三方」。8.2 进一步要求**人工复核 50% 样本**，故另设人工臂
（`measure_grounded_human.py` 按行序奇偶确定性切 50%），实测 **判官臂 94.7% vs 人工臂 94.9%**，
并从判官判 False 的条目里**抓出 3 条误报**（多意图告知文案被当事实 ×2、空答案上幻觉 ×1）。

**（c）被拦下的原始正文必须留痕，否则误报率只能靠重采样近似。**
原实现 guard 判否即回落确定性组装，**原始正文不落盘**。于是测误报率只能「同题同资料重新生成一次再判」，
而重采样常复现不出当初那句话——实测中 T-04 的 `detail`「怕妲己这类高爆发法师」是典型 G3 越界形态，
却因重采样判成误报。本轮改为 guard 判否时把原文写进 `debug.generation.raw_answer`，
脚本优先判当初真正被拦的那一段（`source=captured`），旧记录才回退重采样并标注，两者不混算。

**（d）会话清理直接调 checkpointer，不自建表。**
`thread_id = session_id` 是 4.8-4 定的唯一口径；`DELETE /api/session/{id}` 直接调
`AsyncSqliteSaver.adelete_thread`，另存一份删除记录等于制造第二个口径（本项目反复踩过的坑）。
删除前先 `await cp.setup()`：LangGraph 的 checkpoint 表**惰性创建**，对「建库后还没聊过」的会话
直接 DELETE 会抛 `no such table: checkpoints`，明明无事可删却报 500，与「幂等清空」语义相悖。

**（e）被否掉的替代方案。**
- 「只用覆盖集 30 条」→ 否。测不出泛化能力，且小样本置信区间过宽。
- 「用规则判官（复用 guard 正则）」→ 否。自证，且识别不了「换个说法但仍是越界」。
- 「让 LLM 判官给 1~10 分」→ 否。连续分无法对齐「有据/无据」的二元裁定，且与 guard 的 TP/FP 口径不通。
- 「评测脚本解析 SSE」→ 否。5.2 明确 `/api/chat/sync` 存在的理由就是给评测批量跑分用。
- 「句级增量校验改善首 token」→ 否，**由实测数字否掉**（收益 0.00s，见报告 §2.5）。

## 2. 会被问什么？

1. **「85.1% 的自由问句准确率，是不是说明你的意图路由不行？」**
   → 先给结构：11 条错误**全部**是「关键词表覆盖不到自由口语」这一种根因，没有一条是路由逻辑判错；
   再给对照：同一批 108 条上 LLM 路径只有 41.7%，且延迟 330 倍。
2. **「guard 误报率是多少？分母为 0 你怎么交代？」**
   → 承认最终跑批分母为 0（放松后不再触发），另用**受控探针**（同一批模型回答过两套规则）
   得到放松前 100% 误报率，据此放松；并说明「分母为 0」是放松的必然结果而非回避。
3. **「首 token 4.22s 超了目标，为什么不在 M6 改？」**
   → 因为**实测数据否决了改法**：整段答案只有 1 句，句级校验收益 0.00s；
   且跨句类别外推会漏检（「妲己克制后羿。它是高爆发法师。」第二句才暴露）。
4. **「多意图为什么永久不做？」**
   → 占比 4.3%，且 5 条里 4 条是**关键词误命中**（「搭配」命中 SYNERGY、「对线」命中 MATCHUP），
   1 条是同一关系的两种说法——为误命中做合并是把复杂度花在噪声上。
5. **「判官是 LLM，它自己判错怎么办？」**
   → 承认判官不是独立第三方；对策是①判 False 全列原文供人工复核；②`judge_error` 从分母剔除并计数；
   ③判官与 guard 共用 rubric 使两数可互证；④**人工臂复核 50%**。实测人工臂与判官臂差 **0.2pt**
   （94.9% vs 94.7%），并抓出判官 **3 条误报**（多意图告知文案 ×2、空答案幻觉 ×1）——
   **发现误报却不改判官 prompt 去凑高**，因为口径一旦为结果让步就不可信。
6. **「评测集是不是你为了凑指标改过？」**
   → 没有。11 条意图错误**全列不删**、未改任何 `expect_type`；泛化集 Recall@5 是 n/a 也照实写。

## 3. 怎么答？（要点提纲，不是背诵稿）

- **先讲「为什么可信」，再讲「数字是多少」。** 评测装置的价值在口径：双集分离、判据单一来源、
  分母为 0 的处理、判官失败的剔除规则——这些讲清楚，数字才有意义。
- **不达标项要主动说，且要带根因。** 首 token 4.22s / 长尾 29.3s / 泛化 Recall n/a，
  三条都是主动列出的；「如实记录不达标的归因，本身就比全绿更有说服力」。
- **每个裁定都要能追到一个数字。** 多意图 ← 4.3%；`route_llm` ← 88.9% vs 41.7%；
  阈值 ← 实测区间 0.454~0.850；句级校验 ← 0.00s 收益。
- **方法论修正要点名。** `raw_answer` 留痕修的是「重采样会把真越界记成误报」——
  能说清「我发现的缺陷 + 我怎么修的」，比只报数强。
