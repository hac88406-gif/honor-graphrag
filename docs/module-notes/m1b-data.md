# M1b 模块说明 — 数据层（全量入库阶段）

> 规格书 9.1-1：每个模块交付时附带三段说明（为什么这么设计 / 会被问什么 / 怎么答）。
> 覆盖 M1b 相对 M1a 的增量：全量 133 英雄入库、统一 `get_collection()` 入口、计数三层口径、四项回归用例；
> 对应交付报告 [`docs/milestones/M1b-report.md`](../milestones/M1b-report.md)。

## 1. 为什么这么设计

**全量入库后，桩节点机制自然消失（`stub_heroes = 0`）。** M1a 只入 5 个英雄时，关系端点会指向未入库的英雄，
必须建「桩节点」占位才不破坏图完整性。M1b 把 133 个英雄全量入库后，**所有关系端点都落在真实节点上**，
桩节点预期归零——这不是新功能，而是**M1a 的临时机制按设计退出**。保留建桩逻辑仅为兼容部分入库场景。

**统一 `get_collection()` 入口是硬约束，不是风格偏好（规格书 4.6）。** chromadb 1.5.9 下**重开 collection
不显式传 embedding function 会回退到默认 ONNX 模型**（all-MiniLM-L6-v2）并联网下载。后果是**查询向量与写入
向量不同源**——相似度彻底失去意义、召回静默失效，**且不报错**。这类「无报错的错误」是本项目一路在防的，
故把 EF 配置收敛到唯一入口 `app/utils/chroma.py::get_collection()`，全项目禁止裸取 collection。
`tests/unit/test_retrieval_chroma.py::test_ef_restart_regression` 把它钉成回归用例。

**计数必须标三层口径（2026-10-14 起全项目统一）。** 同一件事有三个合理数字，不标层级就会跨阶段对账混乱
（M1a 报告就曾因此把 Neo4j 去重后的 99 当成 `relations.json` 的 100 写错，见 M1a 报告 §4.2）：
- **源数据层**：`parsed/relations_all.json` — 798 行（COUNTERS 532 / SYNERGIZES 266）；
- **导出层**：`data/graph/relations.json` — 798 行，**未去重**；
- **入库后层**：Neo4j 按唯一键 `起点+类型+终点+patch` MERGE 去重 — **793 边**（COUNTERS 527）。
差 5 条 = 5 条 COUNTERS 被两处官方页面各述一次（清单见 `data/REVIEW.md` §4.2）。
**原则：所有计数一律以脚本/查询统计为准，不手数**，并在引用处标注层级。

**数据画像不是报表，是 M6 评测集的素材来源。** `scripts/data_profile.py` 算出 COUNTERS 出度/入度分布，
并列出 **`hr3` 反向引用 = 0 的 71 个英雄**——这些英雄从未被任何其他英雄页面列为「被压制英雄」，
问「XX 被谁克制」时图谱**必然返回空**。这是**真实的数据边界**，直接决定 M6 该测「拒答 / 降级」哪些问句：
若不知道这批英雄存在，就会把「知识库确实没有」误判成「检索有 bug」。

**`$in` vs `$contains` 的差异必须现场复现并固化（规格书 4.6 陷阱一）。** 列表字段 `hero_ids` 上用 `$in`
会**静默返回 0 条**——不报错、不警告，结果和「知识库确实没收录这个英雄」长得完全一样。
`init_chroma.py` 每次跑都打印一次对照（`$in` 命中 0 / `$contains` 命中 >0），并固化为
`test_list_field_operator_in_vs_contains`，库版本升级改了行为会立刻报警。

**C1 语料改为「派生数据不入库」（需求方 2026-10-15 裁定）。** C1 与 `data/raw/` 同性质（都是抓取/解析产物），
故一并 gitignore、由 `scripts/build_guides.py` 从快照**确定性重建**。这样仓库内**不含官方表达性文本**，
版权顾虑消失，而本地重建后语料完整、检索质量不受影响。**重建必须确定**：`publish_date` 取自快照
`fetch_meta.json.generated_at`，**不用 `date.today()`**——否则隔天重跑同一快照会产出不同语料。

## 2. 会被问什么

1. 为什么 M1a 要建桩节点、M1b 又不需要了？
2. 为什么必须统一 `get_collection()`？裸取 collection 会怎样？
3. 同一个关系数为什么有 798 / 798 / 793 三个值？到底哪个对？
4. 数据画像除了「好看」有什么用？
5. `hero_ids` 用 `$in` 和 `$contains` 有什么区别？用错会怎样？
6. C1 语料为什么不入库？不入库会不会影响检索质量？
7. 为什么重建语料不能把日期写成 `date.today()`？
8. 那 5 条「重复边」是哪来的？合并对不对？

## 3. 怎么答

- **桩节点**：M1a 只入 5 个英雄时，关系端点会指向未入库的英雄，需要桩占位；M1b 全量入库后端点全在真实节点上，
  `stub_heroes = 0`，是临时机制按设计退出。
- **统一 EF 入口**：裸取 collection 会回退默认 ONNX 模型 → 查询与写入**不同向量空间** → 相似度无意义、
  召回静默失效且不报错。故收敛到 `get_collection()` 唯一入口 + `test_ef_restart_regression` 回归。
- **三个数字**：798 = 源数据层行数（`parsed` / `relations.json`，未去重）；793 = 入库后层（Neo4j 按唯一键 MERGE
  去重）。差 5 条 = 5 条 COUNTERS 被两处官方页各述一次，**合并是对的**（同事实同方向，按 `起点+类型+终点+patch`
  去重）。**关键不是记住哪个数，而是引用时标层级**。
- **数据画像的用途**：它算出「71 个英雄 `hr3` 反向引用 = 0」这一边界清单——问这些英雄「被谁克制」时图谱必然空。
  这是 M6 拒答/降级用例的直接素材，避免把「数据确实没有」误判成「检索有 bug」。
- **`$in` vs `$contains`**：`$in` 语义是「字段值等于集合中某一项」，用在**列表字段**上静默匹配不到；
  `$contains` 才是列表成员匹配。差异已由 pytest + 每次导入的现场对照固化，表现为「检索不到」而非报错。
- **C1 不入库**：C1 是抓取/解析的**派生数据**，与 `data/raw/` 同性质，故 gitignore + 由脚本重建。
  库内因此不含官方表达性文本（版权顾虑消失），本地重建后语料完整，**检索质量不受影响**（M2/M6 数据层复跑校验已确认）。
- **不用 `date.today()`**：否则隔天重跑同一快照产出不同语料，与「可确定重建」矛盾。用快照的
  `fetch_meta.json.generated_at` 保证「同一快照 → 同一语料」。
- **5 条重复边**：花木兰→墨子、兰陵王→鲁班七号、孙膑→李白、王昭君→吕布、露娜→虞姬，被两处官方页面各述一次，
  事实与方向一致，MERGE 合并为 1 条边，语料与图谱不冲突。
