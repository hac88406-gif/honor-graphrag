# M1a 模块说明 — 数据层（抓取与样例阶段）

> 规格书 9.1-1：每个模块交付时附带三段说明（为什么这么设计 / 会被问什么 / 怎么答）。
> 覆盖 `scripts/fetch_official.py`、`build_graph_data.py`、`build_guides.py`、`init_graph.py`、`init_chroma.py`
> 与 `data/` 产物；对应交付报告 [`docs/milestones/M1a-report.md`](../milestones/M1a-report.md)。

## 1. 为什么这么设计

**写脚本抓取，不让 AI「上网找」（规格书 1.1b）。** 让模型自己检索再复述，得到的是**不可复现的二手转述**：
同一问题两次问可能给出不同来源，且无法核验「官网上到底写没写这句」。脚本抓取把事实钉在**官方原文 + 快照**上——
数据可复跑、每条都带 `source` URL、可逐条点回页面核对。这是本项目「可追溯」的地基，M6 评测的 Recall@5
与答案有据率都建立在它之上。

**抓取抓全量、入库只入 5 个（规格书 6.4 两步走）。** 抓取 133 个英雄约 2 分钟，一次性做完可以**尽早拿到
覆盖率统计与完整快照**；而入库阶段先只入 5 个样例英雄，是为了**先通过需求方审核再扩量**——
若数据格式（分路编码、装备/铭文 ID 映射、关系方向）判错，在 5 个英雄上暴露比在全量上暴露便宜得多。
因此 M1a 的快照是全量的、`data/graph/` 是子集的，这是**有意的两阶段口径**，不是遗漏。

**文本原样聚合，不做改写（C1，规格书 6.2）。** C1 = 官方详情页的「克制/搭档理由 + 技能描述 + 铭文说明 + 出装说明」
按英雄聚合，**逐字取自抓取快照**。这样语料与图谱关系**同源**——图谱里的「A 克制 B，理由 X」与语料里那句
「A 克制 B，理由 X」是同一份原文，**天然一致**，不需要额外做一致性校验。若改成改写或摘要，就会引入
「语料说的和图谱说的不一样」这类无法自动发现的漂移。

**C2 由模型撰写、与 C1 分离标注。** C2 = 5 篇「对线思路」，事实源是官方页面但**表达由 LLM 生成**
（`data_source=llm_assisted`）。它与 C1 的关键差别是**不可当作官方口径引用**，故在 `data/REVIEW.md` §3.1
单列待审、并在 README 数据声明里显式点出——把生成内容伪装成官方内容是本项目明确要避免的事。

**抓取脚本自带三道断言（9.1-3 的抓取侧对应）。** ① 每个名称/理由/技能描述过 `assert_no_mojibake`
（GBK 解码陷阱：页面是 GBK，解错不报错只出乱码，会静默污染语料）；② 关系区块做**配对断言**
（英雄列表长度 == 理由列表长度，不等即抛错并写 `fetch_errors.log`）——否则会静默错配，
「张冠李戴」地把 A 的理由挂到 B 上；③ 限速 0.6s/请求，避免对官方站点造成压力。

**分层落盘：raw 快照 → parsed → graph/guides。** 快照目录带时间戳且**只增不改**，解析结果与入库数据由它派生。
好处是**重解析不需要重抓**：官方页面结构变了或解析逻辑改了，对着老快照重跑即可，抓取成本与解析成本解耦。

## 2. 会被问什么

1. 为什么抓取要写脚本，不让模型直接上网找资料？
2. 为什么 M1a 抓全量 133 个英雄、却只入库 5 个？这不是「没做完」吗？
3. C1 和 C2 有什么区别？为什么必须分开标注？
4. 中文乱码怎么保证的？不做检查会怎样？
5. 「关系配对断言」是什么？为什么值得单写一道断言？
6. 为什么要保留 raw 快照，而不是只留解析后的 JSON？
7. 抓取为什么要限速？限多少？
8. 数据是官方公开页面，为什么还要做版权声明？

## 3. 怎么答

- **脚本抓取**：模型上网找 = 不可复现的二手转述，无法核验。脚本抓取把事实钉在官方原文 + 快照上，可复跑、
  可逐条追溯 `source` URL。
- **抓全量 / 入 5 个**：两阶段是刻意的风险控制——先在小样本上让需求方审核格式（分路编码、ID 映射、关系方向），
  格式判错的代价在 5 个英雄上远小于在全量上。抓取本身一次做完，避免阶段 2 重新抓。
- **C1 vs C2**：C1 是官方原文聚合（逐字、同源、可当依据）；C2 是 LLM 撰写的对线思路（事实源官方、表达为生成，
  `llm_assisted`）。差别在「能不能当官方口径引用」，故必须分开标注、分开审核。
- **乱码**：页面 GBK，解码错**不报错只出乱码**，会静默污染语料。故对每个名称/理由/描述跑 `assert_no_mojibake`，
  抓取即失败。抽查证据见 M1a 报告 §2.6。
- **配对断言**：页面每个区块给「英雄列表」和「理由列表」两个数组，长度不一致就是解析错配，
  会把 A 的理由挂到 B 上且**不报错**。故断言等长，不等即抛 `RelationPairError` 并写日志（`fetch_errors.log` 不存在即全过）。
- **留 raw 快照**：解析与抓取解耦。官方改版或解析逻辑迭代时，对着老快照重跑即可，不必重新抓取；
  也让「数据从哪来」这件事在本地有实物凭证。
- **限速**：0.6s/请求（规格书要求 ≥0.5s）。既合规，也让失败可重试（脚本带快照缓存，重复执行命中缓存、秒回）。
- **版权声明**：虽然是公开页面，但**官方表达性文本的再分发**仍有版权顾虑。故采取「库内不含全量文案」策略：
  C1 与 `data/raw/` 均不入库、由脚本重建，README 显式声明仅用于技术演示与学习、未用于商业用途。
  **这既是合规动作，也是 6.5 要求的主动声明**——把边界说清楚比藏着更有说服力。
