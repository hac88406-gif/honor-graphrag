# M2 模块说明 — 检索层

> 规格书 9.1-1：每个模块交付时附带三段说明（为什么这么设计 / 会被问什么 / 怎么答）。
> 覆盖 `app/retrieval/` 五个模块：实体链接、意图路由、Cypher 模板 + Neo4j 封装、Chroma 向量检索、BM25 + RRF。

## 1. 为什么这么设计

**实体链接规则优先、不调大模型（规格书 4.3 已裁定）。**
别名表 + 拼音音节编辑距离都是确定性的，可单测、可缓存、零延迟。让 LLM 做实体链接只会引入延迟与不稳定，而收益为零——输入域是王者问答，实体是封闭的 133 英雄 + 115 装备 + 93 铭文 + 5 分路。三级策略「精确 → 别名 → 拼音模糊」命中即停，把绝大多数输入挡在前两级（零成本），模糊匹配只在全失败时兜底。

**模糊匹配用「拼音音节序列编辑距离」而不是「整串字符编辑距离」。**
中文输入错误集中在同音/近音字：凯→铠、貂禅→貂蝉、后一→后羿、兰凌王→兰陵王。音节序列能把同音错字直接归零（拼音完全相同），比字符编辑距离更贴合真实错误分布。编辑距离→置信度映射 `{0:1.0, 1:0.8, 2:0.6}`，让「距离 ≤2」成为必要非充分条件，最终由 `ENTITY_CONFIDENCE_THRESHOLD(0.7)` 把关——距离 2 的候选落到 0.6 被拒，避免过度宽松。

**意图路由默认走确定性关键词规则，LLM 路径为可选增强。**
规格书 4.2 步骤[1]原写「意图识别（LLM）」，但意图枚举封闭（4.4 明确不得新增）、且输入已带实体链接结果（4.3），关键词覆盖足够。确定性 = 可单测、零延迟、离线可跑，正好匹配 M2 验收「全为确定性断言」。LLM 路径（Ollama 结构化输出）保留以对接 4.11 的 qwen2.5:3b，且任何异常一律回落规则路径——外部调用必须有超时与异常处理（9.1-3）。

**7 个参数化 Cypher 模板，不用自由 Text2Cypher（4.7 已裁定）。**
schema 只有 4 类节点、4 类关系，意图是封闭枚举，模板可穷举。自由生成 Cypher 在窄 schema 上是「用不可靠的手段解决确定性问题」：收益为零、风险非零。模板化的好处是可靠性、安全性（参数化根治注入）、可测试性（每个模板可单测）、可缓存性四者兼得。

**方向性是本层最容易写错的地方（规格书 4.4 点名）。**
`COUNTERS_BY_HERO`（X 被谁克制）= 入边，`COUNTERS_OF_HERO`（X 克制谁）= 出边。方向写反时查询**返回结果而不是报错**（静默错误），所以必须为两者各写断言：静态断言模板文本的箭头方向，动态断言「出边查询的 subject 恒为被查英雄、入边查询的 target 恒为被查英雄」，再用一条已知单向边（兰陵王→李白）做正反交叉验证。

**hero 过滤必须用 `$contains` 而非 `$in`（规格书 4.6 v1.4 修正）。**
chromadb 1.5.9 下对**列表字段**用 `$in` 会**静默返回空**——不报错、不警告，结果和「知识库确实没收录这个英雄」长得完全一样。故 `build_where()` 按字段类型选算子：`patch`（标量）用 `$in`，`hero_ids`（列表）用 `$contains`。这条差异由 pytest 固化（`$in` 返回空 / `$contains` 有命中），库版本升级改了行为会立刻报警。

**BM25 混合检索 + RRF 融合（规格书 4.6 加分项，10 号裁定 v1 加上）。**
英雄名、装备名这类专有名词对纯语义模型不敏感（bge 会把「铠」和「凯」当近义），但 BM25 能精确命中字面。中文分词必须用 jieba（rank_bm25 无中文分词能力）。融合用 RRF：`score(d) = Σ 1/(k + rank_r(d))`，只吃排名不吃分数，因此不需要把余弦相似度与 BM25 分值归一化到同一量纲——这正是它在异构检索器融合上稳健的原因。

**所有外部调用都有超时与异常处理（9.1-3）。**
Chroma 查询失败抛 `VectorStoreUnavailable`，Neo4j 查询失败抛 `GraphUnavailable`，供 M3 编排层降级为纯向量检索（M3 验收项：模拟 Neo4j 断开时返回 200 而非 500）。

## 2. 会被问什么

1. 实体链接为什么不用 LLM？错别字/昵称怎么处理？
2. 为什么模糊匹配用拼音编辑距离而不是字符编辑距离？阈值怎么定的？
3. 意图路由为什么先规则后 LLM？规则覆盖不够怎么办？
4. 为什么不用 Text2Cypher？模板注册表有什么好处？
5. `COUNTER_BY` 和 `COUNTER_OF` 的方向怎么保证不写反？写反了会怎样？
6. `hero_ids` 为什么用 `$contains` 而不是 `$in`？用错会怎样？
7. 重开 collection 为什么要显式传 embedding function？
8. BM25 和向量两路分数不同量纲，怎么融合？RRF 为什么有效？

## 3. 怎么答

- **实体链接不用 LLM**：实体是封闭集合，别名表 + 拼音模糊是确定性的，可单测、可缓存、零延迟；LLM 只会引入延迟与不稳定。错别字走别名表（同音错字对人工维护），未收录的走拼音音节编辑距离兜底。
- **拼音编辑距离 vs 字符编辑距离**：中文错字多在同音/近音，音节序列把同音错误直接归零；映射 `{0:1.0,1:0.8,2:0.6}` + 0.7 阈值，让「距离 2」被拒，既不漏也不滥。
- **规则优先**：意图封闭 + 输入已带实体，关键词够用；确定性便于单测与评测。LLM 路径保留、异常回落，作为 M6 评测不达标时的切换位。
- **不用 Text2Cypher**：窄 schema + 封闭意图 → 模板可穷举；模板化同时解决可靠性、注入安全、可测试、可缓存四个问题。
- **方向性**：被谁克制 = 入边 `(x)-[:COUNTERS]->(k{id:$hero_id})`，克制谁 = 出边 `(k{id:$hero_id})-[:COUNTERS]->(x)`。写反不报错只返回错结果，故用「subject/target 恒为被查英雄」断言 + 已知单向边交叉验证双重固化。
- **`$contains`**：`$in` 语义是「字段值等于集合中某一项」，用在列表字段上静默匹配不到；`$contains` 才是列表成员匹配。差异已由 pytest 固化，表现为「检索不到」而你会以为「知识库没数据」。
- **显式传 EF**：裸取 collection 会回退默认 ONNX 模型（all-MiniLM-L6-v2）并联网下载，查询向量与写入向量不同源 → 相似度无意义、召回静默失效。故全项目收敛到唯一入口 `get_collection()`。
- **RRF 融合**：只吃排名不吃分数，规避了余弦相似度与 BM25 分值量纲不一致的问题；异构检索器融合的稳健选择。
